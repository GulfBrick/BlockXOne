## Revision-bound qualification (2026-10-07 source package)

The additive source feature `supabase/features/bx1_provider_binding.sql` follows the original provider migration and the accepted application-admission feature. This is a reviewed source-install candidate, not a claim that live databases or hosted settings have changed. Historical applied migrations, original provider proof and existing immutable rows are preserved; old unqualified writer signatures reject new writes after cutover.

Only a current `SUBMITTED`, personal-context investor/customer-organisation admission application can start a session. `DRAFT` and `CHANGES_REQUIRED` must submit/resubmit first. The private binding function matches the immutable `SUBMISSION` details/version/submitted time and derives `individual` for an unversioned individual investor, `company` for an unversioned/v3 entity investor or v2/v3 wealth-manager customer organisation. All require a nonempty bounded full name and uppercase two-letter country; company subjects additionally require a bounded legal name and registration reference. Incomplete or unsupported subjects fail closed. The strict browser instruction contains only `application_id` and `expected_revision`; it cannot select the subject, level or provider client.

The seven-argument restricted binding RPC receives the verified actor/session/application/revision and the server-configured individual level, company level and client ID. It persists the expected subject, case-sensitive level/client and immutable source revision before any SDK token request. Exact retries are idempotent; configuration/subject/source drift cannot rewrite or reuse the binding. The adapter verifies all returned qualification fields against the server expectation, requests the token at the persisted level, and rechecks actor/application state/revision/details before and after the external call. The Sumsub token response remains its real `token`/`userId` contract; no fabricated provider applicant creation or lookup call is added.

Signed webhooks must include `applicantType` (`individual` or `company`) and exact `levelName`/`clientId`. Raw-byte HMAC verification precedes schema admission. The database independently checks these against the frozen binding before duplicate acknowledgement or insertion. The first matching non-manual signed event pins the provider applicant ID under serialization; webhook-manager simulations cannot pin identity or advance genuine ordering. Semantic retries may reorder JSON bytes, but immutable normalized scalars must still match. Binding/event insertion and their append-only machine-source audit receipt are atomic; failed audit insertion rolls back the boundary action.

Only `applicantReviewed` + `reviewStatus: completed` + `GREEN` without a rejection type, or `RED` with `RETRY`/`FINAL`, qualifies as `COMPLETED_REVIEW`. Admitted lifecycle events are `applicantCreated`, `applicantPending`, `applicantOnHold`, `applicantPersonalInfoChanged`, `applicantReset`, `applicantLevelChanged`, `applicantActivated`, `applicantPrechecked`, `applicantAwaitingUser`, `applicantDeactivated` and `applicantDeleted`. They stay `LIFECYCLE`, even with a completed/GREEN snapshot. Unadmitted applicant-action/workflow event families fail closed.

The scoped SQL reader supplies nullable `applicant_type`/`level_name`, `evidence_kind` (`LIFECYCLE`, `COMPLETED_REVIEW`, `LEGACY_UNQUALIFIED`) and `projection_state` (`EFFECTIVE`, `SUPERSEDED`, `MANUAL_TEST`, `LEGACY_UNQUALIFIED`, `REVISION_STALE`, `CONFLICT`). Only `EFFECTIVE` is normalized `CURRENT`. Latest qualified genuine evidence drives progress for the exact currently submitted revision; tied distinct genuine events are explicit conflicts, not delivery-order passes. Genuine deactivation/deletion invalidates an older completed result and directs the applicant to the provider/reviewer. Manual invalidation remains simulation only. Legacy and previous-revision records cannot become effective.

Applicant and reviewer views consume this SQL projection, show type/level/kind/history/conflict and provider-specific next action, and discard tokens/evidence when account, operating context, application, revision or application state changes. A lifecycle GREEN snapshot is never displayed as a completed answer. Loading, empty and error states cannot retain apparent completion. Existing review commands/checklists and all admission/account/role/eligibility/financial/contract decisions remain unchanged. An SDK token or authenticated callback alone grants none of these authorities.
