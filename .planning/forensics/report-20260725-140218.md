# BlockXOne Delivery Loop Forensics

**Date:** 2026-07-25
**Scope:** Why the prior delivery loop stalled, why product work remained unfinished, and what must replace it
**Method:** Read-only Git, planning-artifact, worktree, runtime, prior-task, UI-specification, and GitHub-state inspection
**Verdict:** The autonomous/background retry loop is retired. BlockXOne must proceed through bounded, user-visible checkpoints with explicit proof.

## Problem statement

The user expected a functional, production-ready BlockXOne application with a coherent institutional UI and a protected GitHub source of truth. The prior workflow repeatedly appeared stuck, did not finish product delivery, and left uncertainty over which repository and branch contained the real application.

## Executive finding

This was primarily an orchestration and scope-control failure, not a single code defect.

The active Phase 0 plan concentrated on runner containment, exit-code propagation, evidence provenance, ignored-output handling, and review mechanics. It explicitly prohibited product behavior and UI changes. At the same time, functional product fixes were made in a separate standalone repository and left as eight uncommitted changes. Planning state continued to name a different repository and branch. Long-running foreground/background server activity then made the previous task appear frozen and led to repeated interruptions.

The result was predictable: extensive Phase 0 evidence machinery, no completed production phase, no authoritative GitHub branch for the functional application, and no clean handoff.

## Runtime finding

The functional stack itself is recoverable and was verified locally:

- web: `http://127.0.0.1:23000`
- API health: `http://127.0.0.1:28080/healthz`
- migration: completed successfully
- seed: completed successfully
- API and worker: healthy

The first parallel Compose build encountered a duplicate image-export race because several services built the same target at once. The functional Compose file was corrected so only `api` builds the shared image and `migrate`/`seed` consume it. A later `up -d --build` completed without the race.

Verification then passed:

- all Go packages;
- 4 web test files / 94 tests in the pinned Node 22.23.1 and npm 10.9.8 container;
- production-mode Next.js build for 45 routes with explicit remote HTTPS configuration;
- a fully isolated fresh-volume stack with migration and seed exit 0, healthy API and worker, and HTTP 200 from the API and web;
- removal of the temporary verification project and volumes while the demonstration stack remained available.

## UI/UX finding

The existing native UI specifications already define the correct BlockXOne direction:

- dark graphite foundations;
- restrained cyan-to-blue accent;
- institutional, calm investor experience;
- dense, traceable operator experience;
- Sora for display, IBM Plex Sans for body, and JetBrains Mono for data;
- 150-300 ms transform/opacity motion;
- visible focus, adequate hit targets, and reduced-motion support.

The runtime broadly follows the dark blue/cyan direction, but it has two competing token systems. `design-tokens.css` is close to the specification, while `globals.css` adds light/dark HSL tokens, raw hex values, glass/holographic/neon effects, and separate motion rules. Page components also repeat raw colors, and some Framer Motion timings exceed the intended motion band.

This is a consolidation problem. A new detached design system is not required; the existing UI specifications must become the sole authority and the runtime must be brought into conformance.

## GitHub protection finding

The official repository `GulfBrick/BlockXOne` is private and has one verified administrator/collaborator. There are no deploy keys or webhooks. At initial inspection:

- private repository forking is currently allowed;
- vulnerability alerts are not currently enabled;
- automated security fixes are disabled;
- Actions allows all actions and does not require SHA pinning;
- enforceable branch protection and repository rulesets return GitHub plan-level `403` responses for this private repository.

The API returned no usable two-factor-authentication status. That is not evidence that 2FA is disabled; the account owner must verify it in GitHub settings.

The following protections were then applied and independently verified:

- vulnerability alerts are enabled;
- automated dependency security fixes are enabled and not paused;
- merged branches are deleted automatically.

GitHub rejected changing `allow_forking` with HTTP `422` because that control can only be changed for organization-owned private repositories. The repository therefore remains private, but its reported `allow_forking` field remains `true`. Moving the repository to a protected organization is the available route to that control. No visibility, collaborator, default-branch, or source-code change was made.

## Root-cause analysis

### Primary cause: the workflow optimized the wrong objective

The active plan treated evidence-runner correctness as the delivery objective. The user needed a working product, coherent UI, a staging demonstration, and a protected source of truth. Because product files were outside the plan's allowed scope, progress on the plan could not satisfy the user.

### Contributing cause: no single authoritative repository

Planning state, the runnable source, the legacy repository, and GitHub each pointed to different histories or branches. Product changes could run locally without becoming a durable GitHub deliverable.

### Contributing cause: background-process lifecycle was mixed with task completion

Server startup and monitoring were allowed to occupy the task's control flow. When the process yielded poorly or was interrupted, the entire task looked frozen even though the underlying repository remained recoverable.

### Contributing cause: evidence machinery expanded faster than product phases

Repeated runner and provenance corrections created activity but not product completion. There was no enforced limit that required the next block to produce a user-visible product proof.

## Recovery decision

Do not restart the autonomous loop. Use these bounded checkpoints:

1. **R-01 — Recover and publish a functional baseline**
   - Preserve the eight current changes.
   - Make the functional Compose build deterministic.
   - Run targeted unit tests, build, migration, seed, API health, worker health, and web smoke checks.
   - Commit a reviewed baseline on `codex/functional-platform`.
   - Add the private GitHub repository as the publication remote and push the branch without replacing `main`.

2. **R-02 — Consolidate the UI system**
   - Make the existing Phase 01, Phase 07, and Phase 08 UI specifications authoritative.
   - Consolidate duplicate tokens and fonts.
   - Remove raw page-level colors and decorative neon/holographic drift.
   - Normalize motion to 150-300 ms, limit simultaneous decorative animation, and verify reduced motion, keyboard focus, responsive layout, and contrast.
   - Produce before/after screenshots for investor and operator routes.

3. **R-03 — Functional application closure**
   - Verify investor and operator authentication flows.
   - Verify core API-backed routes and fail-closed states.
   - Replace mock-only dependencies only where the production contract requires it.
   - Add end-to-end smoke tests for the demonstration path.

4. **R-04 — Protected staging**
   - Create a staging deployment contract separate from real production.
   - Use secret-managed services and non-mock providers.
   - Deploy only a saved, tested revision.
   - Capture deployment, rollback, monitoring, and smoke-test receipts.

5. **R-05 — Production gates**
   - Close security, financial-ledger/reconciliation, blockchain-provider, compliance, backup/restore, incident-response, observability, and regulatory gates.
   - Keep production release at NO-GO until every mandatory gate has executable evidence.

## Control rules replacing the loop

- One rock has one user-visible outcome.
- Each rock starts with an allowed-file scope and ends with explicit proof.
- No background service is treated as task completion; it must be started, health-checked, and handed off independently.
- No automatic retry may repeat the same failing command more than once without a changed hypothesis.
- No branch is merged to `main`, no public visibility is enabled, and no production deployment is performed without an explicit checkpoint.
- Every finished rock records the branch, commit, tests, runtime URLs, remaining blockers, and exact next action.

## Immediate next checkpoint

The immediate work is R-01. The application is runnable locally, but the functional changes are not yet a durable, reviewed GitHub branch. UI consolidation follows after the baseline is protected, so visual work is performed on the correct source of truth.
